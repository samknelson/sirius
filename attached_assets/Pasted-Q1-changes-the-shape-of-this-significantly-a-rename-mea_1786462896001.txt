Q1 changes the shape of this significantly — a rename means the S2 row keeps its UUID, so every existing `id_map` row, `employer_policy_history` row, and `denorm_policy_id` stays valid. No drift correction, no remap, no reset. The risk moves entirely into the seeder.

One thing to check before handing this over: **`U` may already be taken.** The runbook describes `seed-migration-policies.ts` as seeding three migration stubs — **RES, TT, and U** — on top of the four base policies (PA, R, EC, COBRA). If the existing stub `U` is a different thing, `U = Inactive` collides. And `RES` may be a Restaurant stub that also needs retiring. Both are in Q1/Q2 below.

## Note for Replit agent

### Context

`load-policies.ts` maps S1 policy references to S2 policy rows via an alias table; `seed-migration-policies.ts` and `bootstrap-target.ts` create the S2 policy catalogue. Two fund rulings need implementing.

### Behavior — Change 1: rename R → UH

`Restaurant Plan` (`sirius_id = R`) is renamed to `Unite Here Plan` (`sirius_id = UH`). Same policy row, new identity. `R` / `Restaurant Plan` is retired and must not exist after this change.

1. The seeders produce `sirius_id = UH`, `name = Unite Here Plan` on a fresh target. `R` / `Restaurant Plan` appears nowhere in seed data.
2. **On an existing target, the seeder must rename, not create.** Resolution order for this policy: match `sirius_id = UH` → else match `sirius_id = R` and update it in place to UH / Unite Here Plan → else create. Skipping the middle step produces a duplicate policy row and orphans every existing mapping — that is the primary failure mode of this change.
3. The rename is counted and reported (`renamedFromR: 1`) so an operator can confirm it happened rather than inferring it from silence.
4. The alias table in `load-policies.ts` targets `UH` wherever it previously targeted `R`.
5. Because this is a rename of the same row, existing `id_map` entries, `employer_policy_history` rows, and `employers.denorm_policy_id` values remain correct and require no correction. Do not add drift-correction logic for this change.
6. If a target somehow contains **both** `R` and `UH` rows, abort with both ids listed rather than guessing which to keep.

### Behavior — Change 2: deleted policy nodes → Inactive

Where an election references a policy nid absent from staging (S1 node deleted) but the elections are live, the reference maps to `sirius_id = U`, `name = Inactive`.

7. When an election's policy nid has no staged `sirius_json_definition` row, write an `id_map` entry pointing that nid at the Inactive policy instead of emitting `policy_ref_not_staged`.
8. Every distinct nid absorbed this way is reported with its election count — e.g. `mappedToInactive: { "8868662": 41 }`. Do not collapse to a single counter; an unexpected nid must be visible.
9. `policy_ref_not_staged` is retired only if (7) fully covers it. Any nid that can't resolve even to Inactive still rejects.
10. If the Inactive policy is absent from the target, abort at startup with a clear message rather than proceeding.
11. `load-employer-policies.ts` (5b) rejects `policy_unmapped` from the same root cause — shops whose `ledger.policy.ebh` references a deleted nid. Confirm it resolves through the new `id_map` entries without a separate code change; if it doesn't, say so rather than working around it.
