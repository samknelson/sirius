## What S1 is

- Drupal 7. Entity-field model: each content field lives in its own

  `field_data_<field>` table, with a `field_revision_<field>` twin for

  history. Records join to `node` on `entity_id = nid`. One logical

  record (member, grievance, trust/benefit election) spans dozens of

  these tables.

- Value column is usually `<field>_value`, but compound fields differ:

  names split into `_given`/`_family`/etc., addresses into

  `_thoroughfare`/`_locality`/`_postal_code`/etc., files into `_fid`,

  entity refs into `_target_id`, taxonomy into `_tid`. The

  `entity_type` + `bundle` columns say which content type each row serves —

  one field table can serve several.

- `sirius_*` tables are custom application tables (ledger, trust/benefit

  scan log, quickhash, etc.), not D7 boilerplate. Treat them as the

  business-logic core.

- Everything loaded as Postgres `text`. Infer real types from the values.

## The S1 data is anonymized — important

- SSNs, names, emails, phones, addresses, and free-text are masked or

  nulled. Structure (types, formats, cardinality, fill rates) is real;

  contents are fake. Don't infer meaning from a specific masked value.

- Some columns are fully nulled. A null column here does NOT mean the

  field is unused in production — note it as "masked, confirm against

  live system" rather than concluding it's empty.

1. **S1 field inventory** — profile each field table from the live

   connection: value-bearing column(s), inferred type, multi-value or not

3. **Transformation logic** — per NEEDS-TRANSFORM: the actual conversion

4. **Entity reassembly** — how you'd join the `field_data_*` tables back

   State where `field_revision_*` history carries over vs is dropped.

5. **Open questions** — anything unresolvable from the (anonymized) data +

   your S2 knowledge. Masked/nulled columns are the likeliest source.
