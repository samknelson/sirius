## Implement Domestic Partner Charges and Payment-Gated Benefits

### Goal

Create a separate **Domestic Partner (DP) account and charge workflow**. A DP must be paid for before receiving coverage, but nonpayment must affect only the DP—not the subscriber’s own benefits.

Keep charge creation separate from the benefit scan.

### Core rules

1. DP and COBRA each use their own new account type.
2. The DP account belongs to the worker/subscriber.
3. It does not affect employer accounts.
4. Create DP charges no more than one coverage month in advance.
5. An unpaid DP charge blocks only the DP’s benefit.
6. The subscriber and DP must still pass all other applicable eligibility rules.
7. Running the charge process repeatedly must never create duplicate charges.

### DP charge-generation job

Build a scheduled, rerunnable job that:

1. Finds active elections containing a domestic partner.
2. Determines the next coverage month.
3. Confirms that the subscriber has a benefit for that month.
4. Checks whether a DP charge already exists for:
   - the account;
   - the DP dependent;
   - the coverage month; and
   - the relevant DP election.
5. If no matching charge exists, create the charge.
6. If one already exists, make no change.

Do not put this charge-generation logic inside the general benefit scan.

### DP account

Add a dedicated DP account or account bucket that:

- belongs to the worker/subscriber;
- records charges by DP dependent and coverage month;
- records payments and their allocation to charges;
- exposes the remaining balance for each month;
- supports payment before the coverage month begins;
- remains separate from normal employee contributions, COBRA, provider accounts, and employer accounts.

Use existing account, ledger, charge, payment, and allocation patterns wherever possible. Do not build a parallel accounting system.

### DP charge plugin

Create a DP eligibility plugin that evaluates the DP dependent—not the subscriber.

For the requested coverage month:

1. Find the applicable DP charge.
2. Determine whether it has been fully paid.
3. Pass only when the required charge has a zero remaining balance.
4. Fail when:
   - no required charge exists; or
   - the charge has an unpaid or partially paid balance.

A failed DP payment check must not remove or block the subscriber’s own benefit.

### Benefit behavior

Grant the DP benefit only when:

- the subscriber has coverage for the requested month;
- the DP election is active for that month;
- all other applicable eligibility plugins pass; and
- the corresponding DP charge is fully paid.

Do not grant DP coverage merely because a payment exists. The subscriber must still be otherwise eligible.

### Scan triggers

Queue or requeue the relevant benefit scan when:

- a DP charge becomes fully paid;
- the DP election changes;
- subscriber eligibility changes;
- a payment allocation changes; or
- a charge is adjusted or reversed.

Never scan more than one coverage month into the future.

### Changes after charge creation

Implement safe handling for these cases:

- **Election ends before the coverage month:** do not grant the DP benefit; use the existing adjustment/reversal pattern for the charge.
- **Subscriber loses eligibility:** do not grant the DP benefit; adjust or reverse the associated charge using existing ledger conventions.
- **Payment is reversed:** requeue eligibility and reevaluate the DP benefit.
- **Multiple DPs:** keep charges and eligibility evaluations separate by dependent.
- **Reruns and retries:** must not duplicate charges or corrupt allocations.

Do not delete posted financial records if the system normally uses offsetting adjustments.

### Worker interface

Using existing UI patterns, allow the worker to:

- see DP charges by coverage month;
- see paid, unpaid, and partially paid status;
- see the amount due;
- make a payment before the coverage month;
- understand that unpaid DP charges affect the DP’s coverage only.

### Acceptance criteria

- [ ] A subscriber with next-month coverage and an active DP election receives one DP charge for that month.
- [ ] Running the job multiple times does not create duplicate charges.
- [ ] No charge is created more than one month ahead.
- [ ] A fully paid charge allows the DP payment plugin to pass.
- [ ] An unpaid or partially paid charge causes the plugin to fail.
- [ ] DP nonpayment does not affect the subscriber’s benefit.
- [ ] Payment completion queues the DP for reevaluation.
- [ ] A DP is not granted coverage if the subscriber fails another eligibility rule.
- [ ] Multiple DPs are evaluated and charged independently.
- [ ] Election and eligibility changes safely adjust or reverse future charges.
- [ ] The account is tied to the worker, not the employer.
- [ ] Existing accounting and eligibility patterns are reused.

### Implementation approach

Before changing code:

1. Inspect the existing account, ledger, payment-allocation, scheduled-job, election, and eligibility-plugin patterns.
2. Identify the closest existing implementation to reuse.
3. Produce a short implementation plan listing the models, services, jobs, plugins, UI components, and tests to change.
4. Call out any unresolved business rules rather than inventing them.
5. Implement in small stages and add tests for every acceptance criterion.

### Business rules still requiring confirmation

Do not hard-code assumptions for:

- DP rate calculation;
- job cadence;
- payment due date;
- grace period;
- treatment of overpayments;
- refund behavior;
- whether one subscriber can have multiple payable DPs;
- exact charge reversal behavior after eligibility loss.
