#167 - Immediate WMB scan with rate cap
What & Why
Time-sensitive worker data changes (payments, cardchecks, COBRA saves, etc.) already enqueue a WMB scan job, but under large queue volume the 5-minute cron can take a long time to reach them. Add an "immediate scan" fast path: when a per-worker job is enqueued from an event-driven trigger source, process it right away — but capped so at most X workers are immediately scanned per minute of clock time, and any given worker is immediately scanned at most once per minute. Anything over the cap simply waits for the existing cron.

Note: this is intentionally NOT a denorm plugin (scans are side-effecting jobs, not derived-table convergence) and NOT tracked via the Variables table or in-memory state (prod is multi-instance ECS; in-memory counters would multiply the cap per instance and reset on deploy). Use the existing flood framework, which is DB-backed, runtime-tunable via flood_<name> variables, and auto-cleaned.

Done looks like
When a worker's data changes via one of the per-worker auto-trigger sources, their scan runs within seconds instead of waiting for the next cron pass — as long as the per-minute budget isn't exhausted.
No more than X immediate scans happen in any minute, tunable at runtime without a deploy; a given worker is immediately scanned at most once per minute.
When the budget is exhausted (or the flood check fails), jobs quietly stay in the queue and the cron processes them as today — no errors surfaced, no duplicate scans.
The whole fast path can be turned off (cap of 0 or a disabled setting), reverting to pure cron behavior.
Log lines make it easy to see when immediate scans ran vs. were deferred to cron.
Out of scope
Changing the cron batch processor, its schedule, or batch sizes.
Prioritizing/reordering jobs within the cron queue itself.
Any UI for monitoring immediate scans (logs are enough for now).
Rate limiting for monthly batch / bulk-hours enqueues (those stay cron-only by design).
Steps
Register flood events for the cap — Add two flood event definitions: a global "immediate WMB scans per minute" cap (default X, tunable via its flood variable) and a per-worker "once per minute" cap keyed on the worker id. Both should fail open toward the cron path: any error in the flood check means "skip immediate, let cron handle it."
Claim-by-id support in the queue — Extend the WMB scan queue storage with a way to atomically claim a specific just-enqueued job (same claiming semantics as claimNextJob, so the cron and the immediate path can never double-process the same job).
Immediate-scan trigger on enqueue — After a per-worker job from an event-driven trigger source is enqueued (the PER_WORKER_AUTO_TRIGGER_SOURCES set), check both flood limits; if within budget, record the flood events, claim that job, and run it through the existing job-processing logic asynchronously (never blocking the request/event handler that caused the enqueue). Ensure this runs only after the enqueue is committed so the claim can see the row.
Guardrails and observability — Make sure an immediate-scan failure records the job result exactly like the cron path (so retries/failure counts behave identically), add clear logging for ran-immediately vs. deferred-to-cron decisions, and provide an off switch (cap 0 disables the fast path).
Smoke tests — Standalone tsx smoke tests covering: under-budget enqueue scans immediately; over-budget enqueue defers to cron; same worker twice in a minute defers the second; flood-check error defers safely; cron never double-processes a claimed job.
