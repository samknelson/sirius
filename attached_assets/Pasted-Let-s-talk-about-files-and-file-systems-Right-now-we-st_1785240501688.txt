Let's talk about files and file systems.

Right now, we store uploaded files as Replit objects. But the current framework has some limitations, and I'd like to extend it. We're going to be attaching lots of files to various entity types in various ways.

For starters, we need to have multiple file systems. Most sites will have a "public" and a "private" file system. Some sites may have additional file systems, like "archive". 

File systems are specified using environment variables and secrets. They're not configurable through the app; the environment variables specify file systems, using an identifier. So the environment might specify "archive" as a filesystem; the application would then have access to use that file system by id.

To start with, there are three different file system providers: "replit", "s3", and "local". So the environment might specify e.g.

[
	archive = [
		name: "Archive",
		access: private,
		provider: replit,
		provider_settings = [
			bucket_id: **uuid**,
			secret_name: FILESYSTEM.ARCHIVE.ACCESS_KEY
		]
	],
	public = [
		name: "Public",
		access: public,
		provider: local,
		provider_settings = [
			base_path: /home/archive/files/
		]
	],
	private = [
	]
]

The "Files" table that currently exists should probably remove the "access_level" field, and instead have a "file system id". I imagine that we'll also want to make the combination [file system, path] unique; each db file should have one and only one live file.

I imagine that we'll want to implement a service structure analagous to comm, so we'll have 
- services/files/base.ts: Offering basic file services (read, write, create, delete)
- services/files/providers/s3.ts
- services/files/providers/local.ts
- services/files/providers/replit.ts

But I'm open to the idea that we wouldn't put this in "services", we'd put it in "storage": 

- storage/files/base.ts
- storage/files/providers/s3.ts
- storage/files/providers/local.ts
- storage/files/providers/replit.ts

Whatever we do, we need to make sure that we keep files in the database and vice versa:

- Every file must have one and only one entry in the "files" table.
- Inserting, updating, or deleting database entries should be connected to the corresponding operation on the file system.
- We'll need a cron sweep to keep things in sync:
	A) For any db record without a corresponding file, mark it as "missing"
	B) For any files without a corresponding db record, delete it (maybe with a confirmation step, or run manually)
	C) Update the db record to ensure that the mime type and size are correct.

I'm going to want a raw "file browser" tool, that lets admins browser through the various file systems, uploading, replacing, or deleting files.
