An additional **3 public families** and **3 embedded workflow groups** are assessed separately. They do not inflate the 50-family denominator. “Missing” is a finding about these inspected help sources, **not** a claim that the page has no inline instructions, that every component is enabled, or that another deployment lacks organization-specific help.

**Recommended first batch:** benefits interpretation and scan safety; enrollment lifecycle; DC preparation/approval; and online payment/status recovery. Safe read-only database checks:

```sql
-- Physical table confirmed from schema and information_schema first.
SELECT id, paths, summary, details FROM help ORDER BY id;
-- Result: zero rows. No local content or IDs to reproduce.

SELECT count(*) AS local_entries,
       count(*) FILTER (WHERE nullif(btrim(details), '') IS NOT NULL)
         AS expanded_entries
FROM help;
-- Result: 0, 0.

-- $1 bound to 497 distinct synthetic route examples extracted from App.tsx.
-- :parameters replaced with "example"; not real entity IDs or browser visits.
SELECT p.path,
       coalesce(array_agg(h.id) FILTER (WHERE h.id IS NOT NULL),
                ARRAY[]::varchar[]) AS matching_ids
FROM unnest($1::text[]) AS p(path)
LEFT JOIN help h ON EXISTS (
  SELECT 1 FROM unnest(h.paths) AS pattern WHERE p.path LIKE pattern
)
GROUP BY p.path ORDER BY p.path;
-- Result: all 497 paths returned [].
```

An initial query used the TypeScript export name `helps` rather than the physical `help` table and failed with “relation does not exist.” That failure was **not** treated as evidence of missing local documentation; the corrected queries above succeeded.

Component overrides were inspected read-only with `SELECT value FROM variables WHERE name = 'components'`. Explicit `true` overrides included BAO, benefits, elections, benefit scan/exemptions, provider/EDI/login, worker relations/login, employer login/company, ledger/payment batches/Stripe/dummy gateway, bulk, facility, cardcheck, SFTP client, and debug. Other components were not asserted enabled: absence from this JSON is **not** “disabled”; runtime resolution falls back to the component registry's defaults (`server/services/component-cache.ts`). No signed-in role/policy results or active plugin configs were inspected. Even explicitly enabled features may require configured policies, rates, credentials, accounts, templates, or entity access.

### Granularity and notation

- A family is a related user goal or reusable workflow, not each tab, ID, report instance, or plugin config. Financial, coverage, and operational workflows are separated where their risk differs.
- Matrix route sets use **finite brace expansion**, not help patterns: `/x/:id{,/edit,/logs}` means exactly `/x/:id`, `/x/:id/edit`, `/x/:id/logs`. Comma-separated alternatives inside braces are exhaustive for that set. `:id` and optional `:paymentTypeId?` are real router parameter notation. **Never paste these templates or braces into help entries.**
- Every example below is synthetic. Substituting `example` for dynamic parameters yields the representative path used for matching; integer date examples are shown where clearer. Matcher matching is independent of whether a record with that ID exists.
- Common source result **H0** = built-in IDs `[]`, local IDs `[]`, expanded help absent (H/D/M). **H1** = built-in ID `system:trust-providers`, local IDs `[]`, `details: null`. These source/ID statements apply individually to every row using them.
- **M** = missing; **S** = summary-only; **N** = simple/no further entry recommended. **A**, **I**, **O** are reserved for adequate, incomplete/outdated, overlap/contradiction; none confirmed here. Unavailable external-local content and browser checks are **unverified**, never counted as missing.
- Route access shorthand: **tab** = `ProtectedRoute` delegates to the named entity tab's permission/policy/component in V; **policy** = evaluated server-side and may allow an owner or staff, not a hardcoded role promise. All authenticated rows also require sign-in. Conditional gates listed are principal gates, not an exhaustive replacement for action authorization.
- Exhaustiveness check: finite expansion of the matrix accounts for **474 distinct route templates**; the remaining **23 distinct templates** are aliases listed below. Together they reconcile to all **497 distinct templates** in R. Default-subview redirects within a family are not separate family counts.
- Main navigation is fetched from `/api/menu`, not a universal static header. The registered default and EDLS menu plugins apply component/permission/policy gates, drop empty groups, substitute the linked worker, and expand active linked employers. A shipped route can legitimately have no link for a particular user/menu. The selected runtime menu and signed-in links remain unverified.

## Ranked documentation backlog

These are grouped content scopes, **not authored entries**. Patterns are proposed examples, not registered. `%` caveats above apply to every dynamic example. Every candidate must follow A's ordered sections (Purpose; Before you start; How to use; Results/statuses; Limitations/problems) with real UI labels, safe fictional examples, and warnings before consequential actions.

### P1 — Understand coverage and avoid unintended live scans

- **User problem/risk:** People can mistake qualification or an old recorded benefit for current coverage, or run a live scan expecting a harmless preview.
- **Scope/patterns:** Explicit `/workers/%/benefits/current`, `/workers/%/benefits/history`, `/workers/%/benefits/eligibility`; separate staff `/workers/%/benefits/scan` and `/workers/%/benefits/exemptions`. Add `/workers/%/benefits/summary` only for its BAO-specific interpretation.
- **Topics:** Recorded benefits versus eligibility/elections; coverage month versus work month; direct/dependent source; last scan, queued/in-progress and failed; test versus live; Start/Continue and Create/Delete/No Change; prerequisites and missing policy/benefit config.
- **Evidence:** `worker-benefits-current.tsx` shows last/queued scans, `activeInCurrentMonth`, dependent source and “No recorded benefits”; scan page sends `mode: test|live`. `server/modules/worker-benefits-scan.ts` checks staff, month/year/mode and includes dependents. Live results report created/deleted/unchanged and per-action errors.
- **Required verification before authoring:** Read `benefits-scan.ts` and current/history response builders through empty, gap, ended, dependent and partial-failure cases. Confirm exact interpretation of current/ended display and queue refresh timing. Do not run even a test scan during this audit. Later UI check with authorized existing data; no promise that every edit instantly changes coverage.

### P2 — Complete the correct enrollment workflow

- **User problem/risk:** Starting the wrong enrollment type or misunderstanding effective dates/dependent changes can create incorrect elections.
- **Scope/patterns:** `/workers/%/elections/current`, `/workers/%/elections/list`, exact `/trust/enrollment-queue`, and `/trust/election/%`, `/trust/election/%/edit` (overlap needs care: the former also matches edit; do not duplicate identical blocks). Generic `/wizards/%` belongs to P7, not enrollment-only instructions.
- **Topics:** First-Time versus Life Event/Open Enrollment/COBRA, employer/policy selection where offered, dependent conflicts, effective date, signature, draft versus posted election and Review; queue filters All/First-Time/Life Event/Open Enrollment/COBRA, not an assumed approval-state queue.
- **Evidence:** Queue filters use `enrollmentType` and **Review**. Registered Open Enrollment requires a configured active window, fixes January 1 of its plan year, and excludes active COBRA. Life Event implementation carries employer/policy/benefits forward and changes dependents only (birth/marriage add; divorce/death remove), rather than a general benefits-change editor.
- **Required verification:** Trace shared enrollment foundation, launch controls, active-election/COBRA guards, signature requirements, dependent component checks, effective-date boundaries, conflict errors and server commit effects. Confirm cancellation does not undo already-created dependent records before describing it. Never turn a proposed task's broader intent into current instructions.

### P3 — Prepare and approve Disability Credit without confusing approval with a grant

- **Required verification:** Inspect route permissions and transition/storage/grant code for create/edit/upload/supersede/delete, approve/deny/withdraw/void and queued release; verify worker tab content separately (do not promise staff chronology/queued-hours UI there).
