# Transformation Logic (per NEEDS-TRANSFORM entry)

Each T# is referenced from [02-mapping.md](02-mapping.md). Global rules first, then the numbered transforms.

## Global rules

> **Revised per [06-strategy-revision.md](06-strategy-revision.md):** the source is **MariaDB 10.6.25**. Source-side reads are MySQL dialect (see 04 for the canonical read shape); S2-side writes remain Postgres via storage. The old rule "everything in S1 is Postgres text" described the retired Neon transload, not S1.

- **Real source types are in `profile/columns.tsv` / [01-field-inventory.md](01-field-inventory.md).** Most D7 field value columns are `varchar(255)`/`longtext` (so text→target validation still applies to *values*), but reference/int columns are real `int(10) unsigned`, `deleted` is `tinyint`, and datetime fields vary — check the inventory per column instead of assuming text. Rows that fail a cast are written to a per-transform rejects file, never silently coerced.
- **Never run against production directly during development.** The dev target is the synthetic-data MariaDB instance (06 §6); the reader takes its DSN from an environment variable and the production DSN exists only inside the HIPAA-scope deployment. Validation output and logs emit **aggregates and counts only — never sample rows**.
- **Idempotency key = S1 id.** Entities upsert on `sirius_id` = the S1 `nid` as text (or `tid` for options); child rows carry the S1 id in `data.s1Nid` when no `sirius_id` column exists. Re-running the ETL is a no-op update.
- **Route through S2 storage, not raw INSERTs.** Named routes: `createContact`/`createOrMatchAddress`/`createPhoneNumber` (`server/storage/contacts.ts`), `upsertWorkerHours` (`server/storage/worker-hours.ts`), unified-options upserts (`server/storage/unified-options.ts`), ledger/payment creates (`server/storage/ledger.ts`), grievance storage (already S1-nid-aware via `server/storage/grievances/sirius-id-generator.ts`), worker-import pattern (`server/storage/sitespecific/btu/worker-import.ts`). Only bulk-fact loads (T18 ledger history, T20 hours) may use batched storage calls inside explicit transactions — still via storage, with notification suppression (ambient request-context flag) so the migration doesn't fan out emails/SMS.
- **Field-table read shape** (used by every transform, MySQL dialect): `SELECT entity_id, delta, <value cols> FROM field_data_<f> WHERE entity_type='node' AND bundle='<b>' AND deleted = 0 AND language = 'und'` — `deleted` is an **integer, compare unquoted**; include `language` explicitly (only `und` exists, but it's part of the PK); always order multi-value fields by `delta`.
- **Load order** (FK-safe): options/taxonomy → contacts → workers → employers/companies/facilities → policies/bargaining units → relationships → benefits catalogue → elections → worker-benefits/coverage (pending N1/N2) → hours → ledger accounts → charges → payments → dispatch (types, groups, jobs, dispatches) → files → comms/bulk → users/roles → bookmarks. (Grievances removed — descoped, 06 §4.3.)

## Numbered transforms

**T1 — worker nids into `workers.sirius_id` (serial).** Insert with explicit `sirius_id = nid`, then `SELECT setval(pg_get_serial_sequence('workers','sirius_id'), max(sirius_id))` once after the load (this runs on **S2's Postgres** — the only setval in the pipeline; source-side SQL is MySQL). Storage `createWorker` path must accept an explicit siriusId for migration mode (it exists as `serial`, so plain inserts with the value are legal).

**T2 — entity-reference remap (generic).** Build an in-memory (or `migration_id_map` scratch table, outside S2's schema) map `s1_nid → s2_id` per entity type as each entity loads. Every `_target_id` column resolves through this map; unresolvable targets go to rejects with the referencing row id. Applies to all `field_*_target_id` columns.

**T3 — SSN.** Live values (snapshot is masked). Normalize to digits-only, re-format to S2's stored convention (verify existing `workers.ssn` rows' format — S2 stores text with a unique constraint), reject non-9-digit values, and pre-check uniqueness (S1 may hold duplicate/placeholder SSNs — collision list goes to open-questions review Q36).

**T4 — taxonomy term → `options_*` remap.** For each vocabulary: upsert every term into the target options table with `sirius_id` = `tid` as text, `name = term name`, `sequence = weight`, extra term-level fields per 02-mapping (e.g. `field_grievance_open → options_grievance_status.open`, `field_sirius_nota → options_gender.nota`, `field_sirius_member_active → options_worker_ws.data`). Resolve hierarchy via `taxonomy_term_hierarchy` (flatten; parent name into `data.parentName` unless the options table has a `parent` column, e.g. `options_worker_ratings.parent`). Resolve `sirius_term_proxy` indirection first: if a consuming field points at a proxy term, follow `field_sirius_term_proxy_target_id`/`field_sirius_term_source` to the real term before remapping. Then every `_tid` consumer looks up `options_*.id` by `sirius_id`. Use the unified-options storage upserts.

**T5 — phone fields → `contact_phone`.** S1 stores bare 10-digit strings. Convert to E.164 (`+1` + digits after stripping non-digits; reject lengths ≠ 10/11). One row per source field with `friendly_name` = Mobile / Primary / Alt / Phone 2 / Fax and `is_primary` on the designated primary. Route through `createPhoneNumber`; skip Twilio validation during bulk load (populate `comm_sms_optin.sms_possible/voice_possible` from the S1 `sirius_phonenumber` registry instead — T14 — rather than re-validating 100k numbers).

**T6 — scalar status → dated history (`worker_wsh` / `worker_msh`).** S1 keeps only the current `_tid` on the worker, but `field_revision_field_sirius_work_status` / `..._member_status` joined to `node_revision.timestamp` yields the change history. Emit one history row per revision where the tid *changed* (collapse consecutive identical revisions), `date = DATE(FROM_UNIXTIME(node_revision.timestamp))` (source-side read), ordered; the latest row becomes current state. **Production caveat:** current-state `field_data_field_sirius_work_status` has only 167 live rows and `member_status` is **multi-valued** (max delta 3) — the multi-value semantics of member status must be understood (concurrent statuses? per-industry, given `field_sirius_industry` is also multi?) before this transform is built. `ms_id` rows also need `industry_id` (from the term's industry linkage — confirm Q37). This is one of the few places `field_revision_*` is used; see 04.

**T7 — dispatch status term → `worker_dispatch_status.status`.** Term names (vocab `sirius_dispatch_job_type`? actually `sirius_worker_dispstatus` tids 1407/1408) remap to S2's status codes via a hand-maintained lookup table written after inspecting live term names (only 2 distinct tids in sample). Seniority date per Q3.

**T8 — HFE.** `field_sirius_dispatch_hfe_until_value` parsed as datetime, date part → `worker_dispatch_hfe.hold_until`. S2 requires `employer_id`; S1's field is worker-global. Decision: create one row per *currently-home employer* or leave employer null-equivalent — blocked on Q4. ⚠ The "identical to availability date" observation was sample-derived; production has only 115 rows of each — verify the overlap with an aggregate query before encoding a skip rule (Q4).

**T9 — EBA.** S1 `Yes/No` flag on worker vs S2 per-date `worker_dispatch_eba(worker_id, ymd)` rows. For workers with `Yes`: emit one row with `ymd` = date of the revision where the flag first became Yes (from `field_revision_field_sirius_dispatch_eba`), falling back to `node.changed`. Confirm semantics Q5.

**T10 — files.** For each referenced `fid`: read `file_managed` (uri `private://…` or S3 via `s3fs_file`), copy the blob from the S1 file store into S2 object storage, insert a `files` row (`file_name = origname`, `mime_type = filemime`, `size = filesize`, `uploaded_at` = `timestamp` unix seconds → datetime, `entity_type`/`entity_id` = the migrated owner, `metadata.s1Fid = fid`, `access_level` per owner type — worker docs private). Requires file-store access (Q38: the DB snapshot has no blobs). `_display=0` attachments are still migrated but marked `metadata.hidden=true`; `_description` → `metadata.description`.

**T11 — names.** `field_sirius_name_*` map 1:1 onto `contacts` name parts (S1's name module columns match S2's contact columns exactly — S2 was modeled on S1). `display_name = trim(concat_ws(' ', given, family))` when S1's computed display is unavailable. Masked columns (`title`, `middle`, `generational`, `credentials`) migrate as-is from live data.

**T12 — contact email.** `contacts.email` is unique in S2. Dedupe: first contact (lowest nid) keeps the email; later duplicates get email in `data.duplicateEmail` and a rejects-report entry. Optionally seed `comm_email_optin(email, optin)` — only if S1 opt-out data is found (Q39; no opt-out field observed in snapshot).

**T13 — addresses.** Merge compound columns: `street = trim(concat_ws(' ', thoroughfare))`, unit into `street` line 2 semantics per `createOrMatchAddress` conventions (`grievance_shop_contact` variant: `co_address` + `co_address_2`). `state = administrative_area`, `city = locality`, `postal_code` (keep leading zeros — cast to text, never int; sample shows 5-digit), `country` default `US`. Geo: `longitude` ← `geo_left`, `latitude` ← `geo_top` (⚠ "degenerate bbox, left=right/top=bottom" was observed in the 10-row sample — assert equality in the ETL and reject rows where it fails rather than trusting the inference). `accuracy` → `accuracy`. Route through `createOrMatchAddress` with validation *disabled* (bulk mode) but `source='s1-migration'`, `needs_review=false` when S1 accuracy was ROOFTOP, else `needs_review=true` so S2's revalidation queue picks them up.

**T14 — Yes/No → boolean.** S1 encodes booleans as text `Yes`/`No` (case-normalize; also observed lowercase `yes`, and tri-state `Yes|No|Inactive` on `field_sirius_member_active` — map `Inactive` per Q37). `'yes' → true`, `'no' → false`, null → null. Applies to: `sms_possible`, `voice_possible`, `ledger_allocated`, `grievance_open`, `nota`, `dispatch_available`, `can_attach`, `can_ir`, `update_rep`, `mustlog`, `notify`, `annual`, `public`, `boolean`, `active`, `aat_required`, `asi`, `availx`, `timeline_show`.

**T15 — relationships.** `worker_relations.worker_1` = owning worker via `field_sirius_contact` (**Q13 structurally closed** — production has the owning-side field on all 35,774 relationship nodes), resolved contact→worker. `worker_2` = worker resolved from `field_sirius_contact_alt` target: if that contact has no worker node, **create a shell worker** (S2 relations join workers, not contacts — same approach S2's DP/COBRA flows use for dependents). `relation_type` via T4 against `options_worker_relation_type.sirius_id`.

**T16 — elections.** Assemble per election nid: `benefit_ids` = ordered array of S2 benefit ids from multi-value `field_sirius_trust_benefits` (max delta 10; resolve via T2, join with `,` to S2's varchar-array convention — match the format `worker_trust_elections.benefit_ids` already uses); `relationship_ids` likewise from `field_sirius_contact_relations` (max delta 7); `enrollment_type` = coded remap of `field_sirius_trust_election_type` term name (live names needed; only 62k of 243k elections carry a type — pick a policy for the rest); policy target NOT stored (S2 derives policy; stash `data.s1PolicyNid`). **Q16 structurally closed:** `worker_id` ← `field_sirius_worker`, `employer_id` ← `field_grievance_shop` (naming trap), `start_ymd`/`end_ymd` ← `field_sirius_date_start`/`_date_end` — all present in production. Insert via trust elections storage so denorms/events fire (with notification suppression).

**T17 — worker-benefit grants → coverage. ⛔ BLOCKED on N1/N2.** S1's `sirius_trust_worker_benefit` node = "this person (subscriber or dependent via `contact_relation`) holds this benefit under this election", now known to carry `date_start`/`date_end`/`worker`/`shop` in production. Separately, **`smf_worker_month` (2.53M nodes) looks like S1's actual per-month coverage record** (06 §4.2). The old plan — regenerate monthly `trust_wmb` via S2's scan over migrated hours/elections — is now a **policy decision, not a default**: regeneration may differ from what S1 actually granted, and retroactively revoking a granted month creates a COBRA event. Resolution order: (1) N1 — determine `field_sirius_json` structure on `smf_worker_month`; (2) N2 — decide migrate-history vs regenerate; (3) then build either the smf_worker_month → `trust_wmb` loader or the scan-regeneration + reconciliation report. Either way, migrate the grant/election linkage (a) first: `worker_trust_elections`-linked coverage with dependent coverage on the election's `relationship_ids`.

**T18 — ledger charges (`sirius_ledger_ar` → `ledger`).** For each row: resolve `ledger_account` nid → `ledger_accounts.id`; resolve `ledger_participant` nid → migrated worker/contact → `getOrCreate ledger_ea(account_id, entity_type, entity_id)`; `amount` = numeric cast of `ledger_amount` (see real column type in 01); `date` = `FROM_UNIXTIME(ledger_ts)` on the read side (values as old as 2000 are legitimate history); `statement_ymd` = first of `date`'s month, computed in the ETL (confirm S2 statement convention); `reference_type/reference_id` = the migrated entity behind `ledger_reference` nid (benefit grant, election, etc. — resolve via T2 map across all entity types; unresolved → `reference_type='s1-unknown'`, raw nid kept). `charge_plugin = 's1-import'` (a dedicated inert plugin id so S2's reconciliation math — which sums base+adjustments per reference — treats imported history as base entries and never re-derives it). Only `ledger_status='Cleared'` rows exist in the sample; if live data has other statuses, decision needed (Q19). Bypass charge plugins entirely; this is historical fact load.

**T19 — payments.** `amount = abs(dollar_amt)` with S2 sign convention (S2 payments are positive credits; S1 sample shows negatives — verify against live sums so migrated balances match S1 balances exactly, Q20). `status`: Cleared→`cleared`, Failed→`failed` (match `ledger_payments.status` vocabulary in code). `date_cleared = date_created` for cleared rows unless a separate cleared-date field exists in production (Q20). `ledger_ea_id` from payer+account per T18. `allocated` from T14 — **do not** replay S2 payment-allocation plugins on import (memory: cleared payments only touch balances via allocation configs); instead migrate S1's own allocation results implicitly through the `sirius_ledger_ar` rows and set `allocated=true` so S2 doesn't re-allocate. Verify per-participant balance parity: `sum(S1 ar) + sum(payments)` vs S2 computed balance, per account.

**T20 — hours (`sirius_payperiod` → `worker_hours`).** Grain: S1 payperiod nodes are per worker × employer × period (`date_start`/`date_end`; ⚠ "monthly" grain was a sample-derived reading — verify the real period distribution with aggregates; `payperiod_type` turned out to have 1 row in production, so it defines nothing). S2 `worker_hours` grain is worker × employer × Y/M/D with unique constraint; convention: period totals land on `day=1` of the period month (matches S2's monthly-wizard convention — verify against `bao_monthly_hours` wizard). **The hours amount / employment-status payload almost certainly lives in `field_sirius_json` (3.61M rows, `longtext`) — N9: determine its structure (aggregates only) before building this transform.** No other value-bearing field table exists for the bundle. Map status text through `wizard_employment_status_mappings` per employer exactly as the monthly wizard does. Route through `upsertWorkerHours` (ON CONFLICT upsert — idempotent by design).

**T21 — dispatch jobs.** Status remap: Pending→`open`+`running=true`, Filled→`filled`, Archived→`archived` (align to `dispatch_jobs.status` values used in code; verify). `start_ymd` = date part of `field_sirius_datetime`. Facility/job-group targets resolve to `facilities.sirius_id` / `dispatch_job_group.sirius_id` rows created first. Non-schema config (`emails`, `nfcns`, `notify`, counts) → `data` jsonb keys, names preserved verbatim for auditability.

**T22 — dispatches.** Status remap: `accepted`→`accepted`, `accepted_secondary`→`accepted` + `data.type='secondary'` (or keep S1 string in `data.s1Status`), `terminated`→`terminated`. Primary/Secondary type folds into `data.type`. Start/end dates come from `field_sirius_date_start` (51,533) / `field_sirius_date_end` (7,114) — confirmed present in production.

**T23 — shop contracts → S2 contracts.** `field_grievance_contract` PDF per shop: migrate the file (T10) and optionally run the existing `scripts/migrate/core/import-contracts-from-pdf.ts` path to build structured `contracts`/`contract_articles`/`contract_sections`. Recommend: file migration automatic; structured extraction manual/per-shop.

**T24 — shop contacts.** `co_name` is a single display-name string → `contacts.display_name` only (do not guess given/family splits). `co_role` free text → seed `options_employer_contact_type` with the distinct live role strings (dedupe case/whitespace), link via `employer_contacts.contact_type_id`. Multi-value `contact_types` tids → one `employer_contacts` row per (contact, employer, type).

**T25 — bulk history.** One `bulk_messages` row per sirius_bulk node (`medium`, `name = node.title`, `send_date = node.created`), body/subject into medium subtable (`bulk_messages_sms.body` ← masked body field — live values; `bulk_messages_email.subject` ← `field_grievance_notify_subject`). Recipients/participants: S1 per-recipient sends live in `sirius_log` rows (T26) — link `bulk_participants` only if a bulk↔log reference exists in production (Q29). Drafts (`status='draft'`) migrate with no participants.

**T26 — sirius_log split.** Partition by `field_sirius_type`: `incoming_sms`/`outgoing_sms` → `comm` (medium `sms`, direction: incoming = `received` set, outgoing = `sent` set, `contact_id` via `field_sirius_log_handler` target resolved to a contact — handler is multi-valued, take the contact-typed target; log nids into `comm.data.s1Nid`) + `comm_sms` (`to`, `body` ← masked message field). All other types (`popup`, `news:view`, `twilio:conversation`, fastload markers) → **archive-only**: do not pollute `winston_logs` (operational log) with legacy history; export to a flat archive table/file unless the business confirms it needs them queryable (Q29).

**T27 — users & roles.** S1 `users` (pass `!disabled` — auth already externalized) → S2 `users` (`email = mail`, name parts unavailable → from linked staff contact if production has one, else email local-part; `is_active = status`; `last_login` = `login` unix seconds → datetime when > 0). `authmap` (if populated in production) → `auth_identities` rows for the Okta provider; otherwise users log in fresh via Okta and match on email. S1 `role` names (masked) → `roles` upsert by name with manual review; `users_roles` → `user_roles` via both maps. **Never migrate** `pass`, `tfa_*`. uid 0/1 (anonymous/superadmin) are skipped.

**T28 — flags → bookmarks.** `flagging(fid, entity_type, entity_id, uid)` → `bookmarks(user_id, entity_type, entity_id)` for flag types that are user bookmarks (`flag` table defines types — masked names, Q34). Entity type/id remapped via T2; flags on entities that don't migrate are dropped.
