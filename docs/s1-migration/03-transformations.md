# Transformation Logic (per NEEDS-TRANSFORM entry)

Each T# is referenced from [02-mapping.md](02-mapping.md). Global rules first, then the numbered transforms.

## Global rules

> **Revised per [06-strategy-revision.md](06-strategy-revision.md):** the source is **MariaDB 10.6.25**. Source-side reads are MySQL dialect (see 04 for the canonical read shape); S2-side writes remain Postgres via storage. The old rule "everything in S1 is Postgres text" described the retired Neon transload, not S1.

- **Real source types are in `profile/columns.tsv` / [01-field-inventory.md](01-field-inventory.md).** Most D7 field value columns are `varchar(255)`/`longtext` (so text→target validation still applies to *values*), but reference/int columns are real `int(10) unsigned`, `deleted` is `tinyint`, and datetime fields vary — check the inventory per column instead of assuming text. Rows that fail a cast are written to a per-transform rejects file, never silently coerced.
- **Never run against production directly during development.** The dev target is the synthetic-data MariaDB instance (06 §6); the reader takes its DSN from an environment variable and the production DSN exists only inside the HIPAA-scope deployment. Validation output and logs emit **aggregates and counts only — never sample rows**.
- **Idempotency key = S1 id.** Entities upsert on `sirius_id` = the S1 `nid` as text (or `tid` for options); child rows carry the S1 id in `data.s1Nid` when no `sirius_id` column exists. Re-running the ETL is a no-op update.
- **Route through S2 storage, not raw INSERTs.** Named routes: `createContact`/`createOrMatchAddress`/`createPhoneNumber` (`server/storage/contacts.ts`), `upsertWorkerHours` (`server/storage/worker-hours.ts`), unified-options upserts (`server/storage/unified-options.ts`), ledger/payment creates (`server/storage/ledger.ts`), grievance storage (already S1-nid-aware via `server/storage/grievances/sirius-id-generator.ts`), worker-import pattern (`server/storage/sitespecific/btu/worker-import.ts`). Only bulk-fact loads (T18 ledger history, T20 hours) may use batched storage calls inside explicit transactions — still via storage, with notification suppression (ambient request-context flag) so the migration doesn't fan out emails/SMS.
- **Timezone conventions — MANDATORY per-field rule (06 §5).** All 22 S1 date fields are D7 `datetime` **strings**; `node.created`/`changed` remain integer unix seconds (timezone-independent). D7's Date module set `tz_handling` per field, and S1 uses two conventions. Getting one backward shifts the value 7–8 hours — enough to slip a DOB, coverage boundary, or late-fee payment across a day/month boundary.

  | Convention | Handling | Fields |
  |---|---|---|
  | **LA wall time** (`tz_handling: none`) — parse literally, NO conversion | naive local time; handle DST gap/overlap explicitly | `field_sirius_dob`, `field_sirius_date_start`, `field_sirius_date_end`, `field_sirius_skill_expire`, `field_sirius_dispatch_eba_dates`, `field_grievance_alert_date`, `field_grievance_alert_waived`, `field_grievance_date`, `field_grievance_date_1`, `field_grievance_date_2`, `field_grievance_hire_date`, `field_grievance_meeting_date`, `field_grievance_resproc_cd`, `field_grievance_resproc_hd`, `field_grievance_status_date`, `field_grievance_valid` |
  | **UTC** (`tz_handling: site`) — convert UTC → America/Los_Angeles | | `field_sirius_datetime`, `field_sirius_datetime_created`, `field_sirius_datetime_completed`, `field_sirius_dispatch_availdate`, `field_sirius_daterepeat`, `field_sirius_dispatch_hfe_until` |

  DST: `none` fields can hold nonexistent (`2026-03-08 02:30`) or ambiguous (`2026-11-01 01:30`) values — **never let the datetime library resolve them silently**; log and report affected rows. Every date transform below (T6, T13, T16–T22 date casts, and all `_value` datetime reads) must consult this table; a transform that touches a date field not listed here is a spec bug — stop and classify the field first. Validation must include a test covering both conventions and both DST edge cases (06 §9.9).
- **Field-table read shape** (used by every transform, MySQL dialect): `SELECT entity_id, delta, <value cols> FROM field_data_<f> WHERE entity_type='node' AND bundle='<b>' AND deleted = 0 AND language = 'und'` — `deleted` is an **integer, compare unquoted**; include `language` explicitly (only `und` exists, but it's part of the PK); always order multi-value fields by `delta`.
- **Load order** (FK-safe): options/taxonomy → contacts → workers → employers/companies → policies → relationships → benefits catalogue → elections → benefit-history **import** (§4.13 — N17 closed 2026-08-05, amended same day: direct import of EVERYTHING — no cutoff) + worker-month tags (keep-list ruled, N24 closed: only "Comms: Received Enrollment Packet") → hours → ledger accounts → charges → payments → files → comms/bulk → users/roles → bookmarks. (Grievances removed — descoped, 06 §4.3. **Dispatch and skills removed entirely — out of scope, 06 §4.7.**)

## Numbered transforms

**T1 — worker `field_sirius_id` into `workers.sirius_id` (serial). RULED 2026-08-06 (supersedes the original nid mapping).** S1 `field_sirius_id` maps exactly to `workers.sirius_id` (numeric-validated); the S1 `nid` is preserved as a `worker_ids` row of type **"Legacy NID"** (type seeded with stable `sirius_id='s1-legacy-nid'` so re-runs find it). The two id spaces are disjoint (nid ≈ 2.4M node counter, field_sirius_id ≈ 600k business series — verified on production). Rules: NO "Sirius ID" `worker_ids` row is created anymore; missing/non-numeric `field_sirius_id` → the worker loads with a **sequence-assigned** sirius_id (above both the staged field_sirius_id range and the DB max) + reject-report note (`sirius_id_assigned` / `sirius_id_not_numeric`) — never silently defaulted; cross-worker `field_sirius_id` collisions reject (`sirius_id_collision`, first/lowest-nid wins). Re-runs repair rows loaded under the old nid mapping in place (sirius_id rewritten, old "Sirius ID" rows replaced by "Legacy NID"). Then `SELECT setval(pg_get_serial_sequence('workers','sirius_id'), max(sirius_id))` once after the load (this runs on **S2's Postgres** — the only setval in the pipeline; source-side SQL is MySQL). Anything keying on `sirius_id == nid` must key on nid via `s1_staging.id_map` instead (id_map semantics unchanged: nid → S2 UUID). Storage `createWorker` path must accept an explicit siriusId for migration mode (it exists as `serial`, so plain inserts with the value are legal).

**T2 — entity-reference remap (generic).** Build an in-memory (or `migration_id_map` scratch table, outside S2's schema) map `s1_nid → s2_id` per entity type as each entity loads. Every `_target_id` column resolves through this map; unresolvable targets go to rejects with the referencing row id. Applies to all `field_*_target_id` columns.

**T3 — SSN.** Live values (snapshot is masked). Normalize to digits-only, re-format to S2's stored convention (verify existing `workers.ssn` rows' format — S2 stores text with a unique constraint), reject non-9-digit values, and pre-check uniqueness (S1 may hold duplicate/placeholder SSNs — collision list goes to open-questions review Q36).

**T4 — taxonomy term → `options_*` remap.** For each vocabulary: upsert every term into the target options table with `sirius_id` = `tid` as text, `name = term name`, `sequence = weight`, extra term-level fields per 02-mapping (e.g. `field_grievance_open → options_grievance_status.open`, `field_sirius_nota → options_gender.nota`, `field_sirius_member_active → options_worker_ws.data`). Resolve hierarchy via `taxonomy_term_hierarchy` (flatten; parent name into `data.parentName` unless the options table has a `parent` column, e.g. `options_worker_ratings.parent`). Resolve `sirius_term_proxy` indirection first: if a consuming field points at a proxy term, follow `field_sirius_term_proxy_target_id`/`field_sirius_term_source` to the real term before remapping. Then every `_tid` consumer looks up `options_*.id` by `sirius_id`. Use the unified-options storage upserts.

**T5 — phone fields → `contact_phone`.** S1 stores bare 10-digit strings. Convert to E.164 (`+1` + digits after stripping non-digits; reject lengths ≠ 10/11). One row per source field with `friendly_name` = Mobile / Primary / Alt / Phone 2 / Fax and `is_primary` on the designated primary. Route through `createPhoneNumber`; skip Twilio validation during bulk load (populate `comm_sms_optin.sms_possible/voice_possible` from the S1 `sirius_phonenumber` registry instead — T14 — rather than re-validating 100k numbers).

**T6 — member status → ordered eligibility-group association (REVISED per 06 §4.8/§4.8a).** Two v2-era plans are dead:

- **`worker_wsh`: nothing to build.** Employment status is DERIVED in S1, never stored — it comes from the hour type of a worker's most recent payperiod *at each employer* (see T20). `field_sirius_work_status` is vestigial (2 live rows); the revision-reconstruction plan is dropped entirely. Do not create a worker-level employment status in S2.
- **`member_status` is NOT a status timeline.** It is a worker→eligibility-group assignment — terms are industry/policy + hours-threshold combinations (e.g. "UNITE HERE Worker — 60 hours"). Multi-valued, max delta 3 (97.8% of assigned workers have exactly one; ~42% have none). **N12 CLOSED (06 v5 §4.8): delta order is NOT meaningful** (reverses v4 — production shows the same pair appears with either term at delta 0). Every multi-assignment crosses industries, so industry disambiguates and delta drops entirely. Mechanical mapping: term → `options_worker_ms` keyed by `sirius_id` = tid, `industry_id` derived from term name but confirmed against `options_industry` (never string-parse alone); one `worker_msh` row per worker per industry. Current state only — no revision reconstruction, no dated history.

**T7 / T8 / T9 — REMOVED (dispatch is out of scope, 06 §4.7).** Dispatch status, HFE, and EBA transforms are not built; their fields are not read.

**T10 — files.** For each referenced `fid`: read `file_managed` (uri `private://…` or S3 via `s3fs_file`), copy the blob from the S1 file store into S2 object storage, insert a `files` row (`file_name = origname`, `mime_type = filemime`, `size = filesize`, `uploaded_at` = `timestamp` unix seconds → datetime, `entity_type`/`entity_id` = the migrated owner, `metadata.s1Fid = fid`, `access_level` per owner type — worker docs private). Requires file-store access (Q38: the DB snapshot has no blobs). `_display=0` attachments are still migrated but marked `metadata.hidden=true`; `_description` → `metadata.description`.

**T11 — names.** `field_sirius_name_*` map 1:1 onto `contacts` name parts (S1's name module columns match S2's contact columns exactly — S2 was modeled on S1). `display_name = trim(concat_ws(' ', given, family))` when S1's computed display is unavailable. Masked columns (`title`, `middle`, `generational`, `credentials`) migrate as-is from live data.

**T12 — contact email.** `contacts.email` is unique in S2. Dedupe: first contact (lowest nid) keeps the email; later duplicates get email in `data.duplicateEmail` and a rejects-report entry. Optionally seed `comm_email_optin(email, optin)` — only if S1 opt-out data is found (Q39; no opt-out field observed in snapshot).

**T13 — addresses.** Merge compound columns: `street = trim(concat_ws(' ', thoroughfare))`, unit into `street` line 2 semantics per `createOrMatchAddress` conventions (`grievance_shop_contact` variant: `co_address` + `co_address_2`). `state = administrative_area`, `city = locality`, `postal_code` (keep leading zeros — cast to text, never int; sample shows 5-digit), `country` default `US`. Geo: `longitude` ← `geo_left`, `latitude` ← `geo_top` (⚠ "degenerate bbox, left=right/top=bottom" was observed in the 10-row sample — assert equality in the ETL and reject rows where it fails rather than trusting the inference). `accuracy` → `accuracy`. **T20 — hours (`sirius_payperiod` → `worker_hours`). Q21 CLOSED — the payload structure is known (06 §4.12).** Hours and hour-type both live inside `field_sirius_json`. Extraction rules, confirmed against all 3,615,475 rows:

1. **`$.totals.hours.total` is the hours figure. Parse as decimal ALWAYS** — the JSON type is INTEGER on 1,981,145 rows and DOUBLE on 1,634,320; a per-row int-vs-float inference produces inconsistent types in one column. **Negative totals load as-is (OPEN-3 CLOSED 2026-08-05):** the 381 negative-hours payperiods are BPA-era legacy corrections — no charges generate from negative hours, and they stay for pension vesting history; T20's sum-per-month behavior nets them correctly.
2. **`$.totals.hours.by_type` is a map keyed by `sirius_hour_type` tid, with exactly ONE key per row observed.** Read as a map, expect one entry; reject/report rows with more. Live tids: 1544 Active, 1682 No Charge, 1637 Terminated, 1634 LOA, 1633 FMLA, 1632 Disability, 1635 Military Leave, 1691 Initial Eligibility, 1662 Deceased, 1701 Event Center Hours Purchasing, 1636 COBRA. The hour-type mapping table needs only the 1600-series plus 1544 — five 900-series legacy terms never occur in data.
3. **`$.entries` keys are provenance** — `import` (3,299,233), `upload` (313,331), `manual` (2,798), plus 71 rows with numeric nid keys. Treat unknown keys as valid; do not assume a closed enum. Record provenance in `worker_hours` `data`/source metadata.
4. **Exactly 10 legacy-format rows** (depth 6, `entries` as ARRAY, `{daily, monthly, payperiod}` totals): **skip explicitly with a logged reason** naming each nid (N18 dispositions them individually). Never silently drop.
5. `by_dept` / `by_type_dept` / `by_dept_type` / `by_day` are denormalized pivots — **recompute in S2 if needed, do not migrate**.
6. **Employment status derives from `by_type` (06 §4.8a):** the hour-type tid of a worker's most recent payperiod at an employer is the worker's state *at that employer* → `worker_hours.employment_status_id` maps from the payperiod's hour type via the tid mapping (take the term list from `sirius_hour_type`, not the vestigial `sirius_work_status` vocabulary). No worker-level status is ever written.

Grain: per worker × employer × period (`date_start`/`date_end`; ⚠ "monthly" grain still needs aggregate verification; `payperiod_type` has 1 row and defines nothing). S2 `worker_hours` grain is worker × employer × Y/M/D; convention: period totals land on `day=1` of the period month (verify against `bao_monthly_hours` wizard). Route through `upsertWorkerHours` (ON CONFLICT upsert — idempotent by design). **Pay-period provenance (Task 414):** after verify, T20 upserts the id_map `payperiod` crosswalk — every contributing payperiod nid → its monthly `worker_hours.id` (many nids per monthly row; OVERWRITE semantics repoint retargeted periods; fully-verified runs retire mappings for S1-deleted sources) — so T18 can resolve AR `ledger_reference` pay-period nids as hour links, and the BAO hourly plugin adopts linked `s1-import` rows as the historical billing base (no double charge on a post-cutover staff save).

## Addendum 2026-08-06 — T27 build conventions (as shipped)

**T27 users & roles (load-users.ts).** Only ACTIVE (`status=1`) S1 accounts
migrate; blocked accounts are counted and reported, never created. uid 0/1
(anonymous/superuser) are excluded at STAGING (`uid > 1`) and defensively
skipped by the loader; any historical uid 0/1 mapping is deactivated and
unmapped on the next run. Lifecycle rerun reconciliation: previously migrated
accounts whose S1 account became blocked or was deleted from staging are
deactivated and their migration-owned worker link + `worker` role revoked
(`deactivatedBlocked`/`deactivatedDeleted`, `reconciliation.lifecycleRevoked`).
`pass`/`tfa_*` are never even SELECTed at staging. Raw Drupal core
tables stage as `s1_staging.raw_users` / `raw_users_roles` / `raw_roles` /
`raw_authmap` (raw_ledger_ar pattern: keyset paging, stale-delete, count
verify). `authmap` stages for AUDIT ONLY and is not loaded — S2 Okta
identities are keyed by the Okta user id (unknown to S1), so pre-creating
identity rows from Drupal authmap would be fiction.

**uid→worker resolution (RULED 2026-08-06, deterministic, load-time):**
`lower(users.mail)` must equal the staged contact email
(`field_sirius_email`) of EXACTLY ONE staged contact that is referenced by
EXACTLY ONE staged worker (`field_sirius_contact`) resolvable through id_map
`worker`. Zero matches → annotation `no_resolvable_worker`; more than one →
annotation `ambiguous_worker_email`. Annotations never block the account —
it migrates UNLINKED and lands on the reconciliation report for staff
review; unlinked people still self-verify via SSN+DOB at first login.
The resolved link is recorded in `users.data` as
`{ migratedWorkerId, workerLinkSource: "s1-user-migration", s1: {uid, name, created} }`
— first-login linking prefers this recorded id over any email heuristic.

**Roles.** S1 `role` names create S2 `roles` with ZERO permissions; D7
built-ins (`anonymous user`, `authenticated user`) are skipped. Name
collisions FAIL CLOSED: an S1 role whose name matches a pre-existing S2 role
(one this migration didn't create, per the `(T27)` description marker, and
that isn't listed in the loader's `APPROVED_ROLE_BINDINGS` allowlist) binds
to a zero-permission `<name> (s1-migrated)` review role instead — it never
inherits the existing role's permissions (privileged names like
"administrator" would escalate). Collisions are reported under
`roles.collisionDetails`. Loader-created roles get a description flagging
them for manual permission review (role→permission mapping is deliberately
NOT migrated; Okta group→role mapping is Task #2).
Linked workers additionally get the `worker` role (created if absent).
Duplicate active mails: lowest uid wins, later uids reject
`duplicate_user_email` (fatal class — triage, then allow observed count).

**Okta pre-provisioning (provision-okta-users.ts).** Idempotent, DRY-RUN BY
DEFAULT; `--execute` + `--only email[,email]` filter (used to run for-real
against ONLY the canary in rehearsal). Existing Okta account with the same
login → reused; >1 Okta match → `ambiguousOkta`, surfaced and skipped, exit 1.
Success records `auth_identities` (providerType `okta`, externalId = Okta user
id = the future OIDC `sub`, metadata `{workerId, preProvisioned: true,
source: "s1-user-migration", s1Uid}`) so first sign-in takes the
existing-identity fast path with zero matching. Resume-safe: an existing okta
identity row = done, skipped. Bulk REAL provisioning is a cutover runbook
step, never part of rehearsal.
