---
name: Removable package safety boundaries
description: Optional source removal must preserve retained auth and identity safety; migration-data correction stays separate.
---

Treat an absent component directory as distinct from a disabled component. Retained authentication selections must not become permission to use a weaker authentication method. T631 synchronization must refuse as a whole without the installed, enabled identity authority; it must not guess worker identity or perform only the non-identity writes.

**Why:** The owner requires removable source builds against databases that still contain previous component tables and settings, without changing intended authentication or worker identity reconciliation. Refusing is safer than silently changing either authority.

**How to apply:** Preserve stable component IDs, independent switches and historical migration identities while changing directory layout. Component-owned behavior belongs behind generic host contracts, not disguised host literals. Freeman migration-artifact data correction remains separate from extraction; source removal is never authorization to delete retained data.

Narrowly typed UI/form participation and component-owned options declarations
belong on existing contribution and options systems, not parallel frameworks.
Disabled or absent UI must preserve saved extension settings.

**Why:** The user wants to understand and approve real invocation seams,
while retaining existing saves, permissions and stored component data.

**How to apply:** Keep extensions scoped to their host operation. Do not use
UI/data preparation callbacks to grant access, replace shared authorization,
or clear settings merely because the owning component cannot render.

Browser contribution declarations must not eagerly import layouts that read
the navigation built from those same contributions. Defer those views until
the contributed route actually renders.

**Why:** This is a real initialization cycle: the navigation collection is
consumed before it exists, even when the production build and typecheck pass.

**How to apply:** Keep declaration modules light and lazy-load route/layout
implementations; verify a real browser entry point after changing discovery.

Exporting a self-registering policy in a generated shared barrel does not
initialize it. Its owner must import it from a live startup path.

**Why:** The modular evaluator reads a runtime registry, not component policy
descriptions; an unimported implementation refuses even authorized users.

**How to apply:** Test registration through component startup and evaluate
both an authorized and unauthorized request, without importing the policy
directly in the test.

T631 arrival remains a schedule-entry integration, not generic authentication.
Do not substitute identifiers or invent credential providers merely to avoid
an actual dependency.

**Why:** The approved extraction scope preserves shared authentication and
forbids new credential-provider frameworks. Extraction must not silently change
the destination's authority.

**How to apply:** Treat alternative arrival destinations or credentials as a
separate product decision, not an extraction workaround.
