---
name: BAO DP coverage-tier transition and "the DP's children"
description: How the DP tier transition is derived from an election and how the DP's children are told apart from the member's own (relation type), plus what is still unconfirmed with the Fund.
---
Rule: the DP tier transition is a function of TWO things — the member's OWN covered lives (member + dependents that are neither a DP nor a DP's child) and whether any of the DP's children are covered. Own lives 1 → `single_to_2party`, or `single_to_family` when the DP's children are covered; own lives 2 → `2party_to_family`; own lives 3+ → `family_to_family_dp` (confirmed no charge) — the last two regardless of DP's children. Never derive the tier from a plain count of non-DP lives: DP + two of the DP's children is Single → Family ($740.12 Kaiser), not a free family month.

The DP's children are identified BY RELATION TYPE ONLY: a Step Child relation (S1 code SC), or any type whose name mentions the partner's child ("Domestic Partner's Child", "DP Child"). The predicates live in one pure shared leaf (`shared/sitespecific/bao/dp-relation-types.ts`) read by the pricing module AND the `worker.dp` access policy; a partner's-child type is NOT a DP (the biller's `%domestic partner%` ILIKE pre-filter is coarse and is re-filtered through the predicate).

**Why:** `worker_relations` is strictly subscriber → dependent, elections list only subscriber-rooted relation ids, the wizards offer every relation type unfiltered, S1 never nested relations, and no election flag exists — so relation type is the only fact that can distinguish the DP's children without new UI. Step Child is the one catalogue type meaning "my partner's child", and a married member cannot have a DP.

**How to apply:** this mapping is PENDING the Fund's confirmation of how staff record a DP's children (Step Child vs a dedicated type). If the ruling differs, change only the shared predicate leaf; do not fork the rule into a plugin. Still unconfirmed and deliberately not implemented: whether the DP's children should also be payment-gated on the DP charge (today only the DP is), and whether a second DP prices at the next tier. Already-billed months are never re-tiered by the cron (verifyEntry re-prices under the STORED transition, because shape changes over time are legitimate) — mis-tiered history needs a manual ledger adjustment.
