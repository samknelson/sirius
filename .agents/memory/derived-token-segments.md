description: Token segments generated from other plugins' declarations must regenerate on late registration, not once at boot.

# Derived token segments

Parts of the token graph are DERIVED rather than hand-written: the options
relations are generated by joining the unified-options metadata with each
entity table's Drizzle foreign keys, so a new options table or a new
referencing column needs no new plugin.

Rule: a derived-segment generator may not assume registration is a boot-only
event. It must sweep the registry once AND subscribe to later registrations
(the token registry exposes a registration listener for exactly this),
walking each new entity kind as it arrives. Guard the generator's own
registrations against re-entrancy, and key the work on the owner kind so a
rescan is free.

**Why:** token plugins register after boot - a notifier module imported late
declares its named record roots then, and derived caches already key on the
registry version for the same reason. A one-shot pass leaves a late plugin
with a valid field catalog but no derived segments: the token validates at
save time on one surface and is unknown on another.

**How to apply:** any future generated segment family, not just options.
Also: a segment derived from a reference is named after the TARGET TABLE,
not the referencing column - a column name means something different under
every parent, and table naming makes the ambiguous case (two FKs into the
same table) detectable, which the generator then skips with a warning
instead of picking a coin-flip winner.

Related: a bare {{kind}} chain is legal when ANY spec producing that kind
declares defaultLeaf; declaring it on the kind's own descriptor plugin
covers every route to the kind (seeded context root, relation) at once, and
the leaf may be a composed field, not just a column.
